# 后台保活与指纹弹出修复说明

修复时间：2026-09-24
修复目标：`无法像微信一样保持在后台` + `电脑需要解锁时手机上不弹指纹`
目标机型：国产 ROM（小米 / 华为 / OPPO / vivo）优先
编译验证：`gradlew :app:assembleDebug` → **BUILD SUCCESSFUL in 6m 51s**（41 tasks，产物 `app/build/outputs/apk/debug/app-debug.apk`）

---

## 一、结论先行

这次修的是**触发入口**，不是解锁协议。解锁握手（协议帧、AES 加解密、`unlockToken` 回传、PC 校验放行）原本就是完整可用的，缺的是「把验证界面送到用户眼前」这一环 —— 原实现只有一条投递在最低优先级渠道上的、需要用户主动点击的通知，并且在退还到桌面/锁屏时没有任何手段主动弹界面。

修复后链路：**PC 请求 → 手机监听 → 高优先级渠道 + 全屏 Intent 直接在锁屏/桌面拉起验证页 → 指纹 → 原连接回传 token → PC 放行**，通知点击作为兜底路径保留。

另一个关键前提已核对 PC 端源码：`BaseUnlockConnection::PerformAuthFlow` 会一直阻塞读等手机响应，TCP/BT 接受连接后都没设 `SO_RCVTIMEO`，**电脑会无限等待**，所以手机端没有响应超时压力，用户可以慢慢按指纹。

## 二、为什么之前保持不住后台

| # | 原因 | 位置 |
|---|---|---|
| 1 | `startForeground()` 只在已有通知权限时调用。Android 13+ 用户拒绝通知权限后，服务不算进入前台，系统数秒内直接杀掉 | `UnlockListenerService` |
| 2 | 前台服务通知挂在 `IMPORTANCE_MIN` + `VISIBILITY_SECRET` 渠道上，国产 ROM 视为可回收的静默通知 | 同上 |
| 3 | 保活主链（5 分钟链式闹钟）用 `setExactAndAllowWhileIdle`，Android 12+ 默认不授予 `SCHEDULE_EXACT_ALARM` → 抛 `SecurityException` 被 catch 吞掉，心跳断链，只剩 WorkManager 的 15 分钟下限 | `KeepAliveReceiver` / `KeepAliveWorker` |
| 4 | `CONNECTIVITY_CHANGE` 静态注册在 targetSdk ≥ 26 已失效，`NetworkStateReceiver` 和 `ServiceRestartReceiver` 的这一路从未执行，少了两条恢复触发点 | `AndroidManifest.xml` |
| 5 | `KeepAliveManager.openAutoStartSettings()` 写好了（覆盖华为/小米/OPPO/vivo/三星）却**全项目从未调用**，用户从未被引导开启自启动/后台弹出界面/锁屏显示 | `MainActivity` |

> 说明：微信的常驻主要靠 ROM 预置白名单 + 可见的常驻通知 + 厂商推送通道，不是纯技术手段。本 App 现在能做到「服务不被轻易回收 + 被回收后自恢复 + 引导用户授权」，但在未开自启动的国产 ROM 上仍不等同于微信。

## 三、逐文件改动

### 1. `service/UnlockListenerService.kt`（核心）
- **拆渠道**：`pcbu_service`（LOW/静默，给前台服务用）+ `pcbu_unlock_request`（HIGH、震动、`VISIBILITY_PUBLIC`，给解锁提醒用）。Android 8+ 通知表现由渠道级别决定，原来写在 Builder 上的 `PRIORITY_HIGH` 是被忽略的。
- **无条件进入前台**：`onStartCommand` 开头即调用 `startForeground()`，任何 action 分支都先进入前台状态。
- **全屏 Intent**：解锁通知加 `setFullScreenIntent(pi, true)` + `setCategory(CATEGORY_ALARM)` + `setPriority(MAX)`；`canUseFullScreenIntent()` 为 false 时自动降级为高优先级横幅并打日志。
- **网络回调替代死广播**：`registerNetworkCallback`（WIFI/CELLULAR/ETHERNET），网络恢复时重建 UDP + 蓝牙监听，`onDestroy` 注销。
- **蓝牙顺序反转**：原来是「读完数据包才弹通知」，而 Android 没给 `BluetoothSocket` 暴露读超时，PC 连上却不发包时协程会永久阻塞、用户永远收不到提示。现在改为**先弹提醒再读包**，读包用 `withTimeoutOrNull(3000)`，超时主动 `closeConnection()` 释放被阻塞的读线程。
- **token 竞态处理**：新增 `CompletableDeferred<String?>`，用户比读包更快完成验证时，`sendBluetoothResponse` 会短暂等待 token，避免回传空 token 导致 PC 校验失败。
- 保活闹钟改走 `KeepAliveManager.scheduleWakeup`。

### 2. `utils/KeepAliveManager.kt`
新增：`canScheduleExactAlarms()` / `scheduleWakeup()`（精确不可用时自动降级 `setAndAllowWhileIdle`）/ `canUseFullScreenIntent()` / `openFullScreenIntentSettings()` / `openBackgroundPopupSettings()`（MIUI 走 `AppPermissionsEditorActivity` + `extra_pkgname`）/ `hasShownGuide()` / `markGuideShown()`。
所有厂商页面跳转统一走 `startSafely()`，组件不存在时退回应用详情页，不会崩。

### 3. `network/udp/UdpBroadcastListener.kt`
- **修致命 bug**：改用 `org.json.JSONObject` 解析。原来的正则 `"key":\s*"([^"]*)"` 只匹配字符串值，而 PC 侧 `pcbuPort` 是数字、`isManual` 是布尔，导致解析必然失败、`onDeviceFound` 永不回调 —— UDP 自动检测整条链路等于没接上。
- 签名改为 `startListening(context, port, callback): Boolean`，绑定同步完成并返回真实结果；原实现是「先启动协程再置标志」，绑定失败后调用方仍以为成功，导致永不重试。
- 增加 `SO_REUSEADDR` 与 `MulticastLock`（部分机型收不到广播报文的原因）。

### 4. `MainActivity.kt` + `navigation/AppNavigation.kt` + `ui/screens/MainScreen.kt`
- `pendingUnlockDeviceId/Name` 两个普通静态变量 → `companion object` 里的 `MutableStateFlow<UnlockRequest?>`。Activity 已在前台时点击通知/全屏 Intent 只回调 `onNewIntent`，普通变量赋值不触发 Compose 重组，验证弹窗就不会出现；`AppNavigation` 相应去掉参数。

### 5. `ui/screens/KeepAliveGuideDialog.kt`（新增）
一次性引导用户配置四项：电池优化白名单 / 自启动·后台运行 / 后台弹出界面·锁屏显示 / 全屏通知，每项一键跳转对应厂商设置页。

### 6. `ui/screens/SettingsScreen.kt`
在设置页增加常驻入口：「自启动·后台弹出界面」「全屏通知权限」，方便用户日后自行补开。

### 7. `receiver/KeepAliveReceiver.kt` + `worker/KeepAliveWorker.kt`
闹钟调度统一交给 `KeepAliveManager.scheduleWakeup`，不再直接调精确闹钟。

# 追加修复：收到解锁请求「直接弹指纹」，不要用户手点一次

修复时间：2026-09-24
用户诉求：*「当 app 收到解锁请求时，app 是出现通知，我需要直接出现指纹解锁，不要用户手点一次」*
编译验证：`gradlew :app:assembleDebug` → **BUILD SUCCESSFUL**，产物 `app/build/outputs/apk/debug/app-debug.apk`（35.2 MB）

## 一、上一版为什么还是一次手点

上一版用的是**全屏 Intent**（`setFullScreenIntent`）。它的真实行为是：

| 屏幕状态 | 系统行为 |
|---|---|
| 熄屏 / 锁屏 | **自动拉起**验证界面（等同来电），免点击 ✅ |
| **亮屏且已解锁（停在桌面）** | 只显示一条 heads-up **横幅**，必须点一下 ❌ |

用户遇到的正是第二种：手机亮着放在桌上、停在桌面，所以只看到通知。这不是代码写错，而是全屏 Intent 的平台设计如此。

## 二、正确机制：后台启动 Activity 的豁免（已核对官方文档）

Android 10（API 29）起禁止后台应用随意启动 Activity。官方文档《活动安全性 / 从后台启动 activity》给出的豁免条件中，普通应用可用的只有两条：

1. **应用已获得用户授予的 `SYSTEM_ALERT_WINDOW`（悬浮窗）权限** ← 本次采用
2. activity 由系统发送的 PendingIntent 启动（即锁屏全屏 Intent 走的那条）

（`START_ACTIVITIES_FROM_BACKGROUND` 是系统应用签名权限，第三方拿不到。）

另有 Android 14（API 34）的行为变更：应用用 `PendingIntent#send()` 时，若想授予**自己**的后台启动特权，**必须显式选择启用** —— 需传 `ActivityOptions` 里 `setPendingIntentBackgroundActivityStartMode(...)`。不传则特权不生效。

> 已用本机 `platforms/android-36/android.jar` 通过 `javap` 核对常量确实存在：
> `MODE_BACKGROUND_ACTIVITY_START_ALLOWED`(API 34) / `ALLOW_IF_VISIBLE`(API 36) / `ALLOW_ALWAYS`(API 36) / `DENIED` / `SYSTEM_DEFINED`。
> 注意：`ALLOW_IF_VISIBLE` 在「应用当前不可见」时会被**直接拒绝**，本场景必须用 `ALLOW_ALWAYS`。

## 三、实现：分层 + 回读校验

`UnlockListenerService` 新增 `deliverUnlockRequest()` 作为唯一投递入口（UDP / 蓝牙 / 服务 Intent 三处统一调用）：

```
收到解锁请求
  │
  ├─ 应用已在前台？ ──是─→ startActivity → onNewIntent → 直接弹指纹（无需任何权限）
  │
  └─ 否 → 直接拉起验证界面（靠悬浮窗权限的后台启动豁免）
            │  Android 14+ 额外带 ActivityOptions（ALLOW_ALWAYS / ALLOWED）
            │
            ├─ 延迟 1.2s 回读 MainActivity.isInForeground
            │      ├─ 已到前台 → ✅ 完成，不发通知，用户零点击
            │      └─ 未到前台 → 被系统/ROM 拦截 → 降级发「高优先级 + 全屏 Intent」通知
            │                        └─ 再等 1.5s 回读：若界面此刻上来了，撤销这条多余通知
            └─ startActivity 直接抛异常 → 直接发通知
```

**为什么要「回读」而不是无脑发通知**：`startActivity` 被拦截时**不会抛异常**，是静默失败。只能延迟回读界面是否真的到了前台，才能区分「成功」与「被拦」。
**为什么还要二次回读**：应用冷启动可能慢于 1.2s，避免出现「指纹弹窗已经出来了，横幅还挂在通知栏」的重复干扰。

## 六、诚实的限制

- **免点击成立的前提是悬浮窗权限**。这是平台硬限制，没有绕过方案：不给悬浮窗权限，亮屏停在桌面时系统只允许通知横幅，必然要手点一次。
- 部分国产 ROM 即使给了悬浮窗权限，还额外要求「后台弹出界面 / 后台启动界面」开关（MIUI `OP_BACKGROUND_START_ACTIVITY`）。引导页与设置页都提供了入口和实时状态显示，便于排查。
- 熄屏/锁屏场景不依赖悬浮窗权限，靠全屏 Intent 即可免点击（Android 14+ 需允许「全屏通知」）。
