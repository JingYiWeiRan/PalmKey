# PcbuApk 项目分析报告

分析时间：2026-09-24
分析范围：`PcbuApk/app`（Android 端，本次工作区）＋ `PcbuApk/server/pcbu-desktop`（PC 端，用于核对协议契约）

---

## 一、项目定位

一套 **「手机蓝牙/网络近场解锁电脑」** 方案，相当于开源项目 *PC Bio Unlock*（`meisapps/pcbiounlock`）Android 客户端的重实现。

- **手机端**：`com.jywr.pcbuapk`，单模块 Kotlin + Jetpack Compose 应用。职责是「配对登记 + 常驻监听 + 生物识别确认」。
- **电脑端**：`pcbu-desktop`，C++/Qt + Boost.Asio + OpenSSL，负责显示配对二维码、提供解锁服务端、注入 Windows 凭据提供程序（CredProv）完成真正的解锁动作。

手机 App 本身**不持有用户密码**，只保存 `passwordKey`，由 PC 用该 key 解出自己的密码明文后解锁 —— 这是原项目的安全设计。

## 二、技术栈

| 维度 | 选型 |
|---|---|
| 语言 / UI | Kotlin 2.0.21 + Jetpack Compose（BOM 2024.09.00）、Material3 |
| 构建 | AGP 8.13.1、Gradle Version Catalog、KSP |

| 其他 | zxing-android-embedded 4.3.0（扫码）、androidx.biometric 1.1.0、WorkManager |

编译参数：`compileSdk = 36`（AGP 新 DSL `compileSdk { version = release(36) }`）、`minSdk = 28`、`targetSdk = 36`、Java 11。

## 四、通信协议（与 PC 端逐字段核对）

**统一 Packet 帧**（`PacketCodec` ↔ `BaseConnection.cpp`）

```
| Header 8B (0xDB065AC7AFDFA4CC, 大端) | PacketID 2B (大端) | Length 2B (大端) | Data |
```

| Packet ID | 方向 | 用途 |
|---|---|---|
| 0x50 / 0x51 | 手机 → PC / PC → 手机 | 配对请求 / 配对响应 |
| 0xB0 | 手机 → PC | 上报 deviceId |
| 0xB1 / 0xB2 | 手机 → PC / PC → 手机 | 解锁请求 / 解锁响应 |

**加密封装**：`IV(16) + Salt(16) + Ciphertext + GCM_Tag(16)`，密钥由 `PBKDF2-HMAC-SHA256(password=encKey, salt, 65535, 256bit)` 派生，**明文前 8 字节为毫秒时间戳**，双端均校验 ±120 秒窗口。

> ✅ 已逐项比对：魔数有符号表示 `-2664342315847408436L` 与 `0xDB065AC7AFDFA4CC` 一致；大端序、ID 定义、加密封装、时间戳位置、PBKDF2 参数（`EVP_sha256` = `PBKDF2WithHmacSHA256`）**全部对得上**。协议层是可信的。

**四条链路**

1. **TCP 配对**：手机扫 PC 二维码（`{ip, port, method, encKey}`）→ 连 PC `pairingServerPort` → 发加密 `PairPacketInit` → 收 `PairingResponse`（含 `deviceId / passwordKey / port / macAddress`）→ 存 Room。
2. **TCP 解锁**：手机连 PC `unlockServerPort` → 发 `deviceId` + `unlockRequest(encData)` → PC 解密并用 `passwordKey` 还原密码 → 回 `unlockResponse` → 手机校验 `unlockToken` 回显一致。
3. **蓝牙解锁**：**反向**。手机作为 RFCOMM 服务端常驻监听（UUID `62182bf7-...-c5f2008bdf`），PC 在锁屏时用 `BTUnlockClient` 连入并下发 `UnlockRequest`，手机弹通知 → 用户生物识别 → 手机经同一 socket 回 `UnlockResponse`。
4. **UDP 广播**：PC 每 2 秒向 `255.255.255.255:<udpPort>` 广播 `{deviceId, pcbuIP, pcbuPort, isManual}`，手机据此判断「电脑在附近」。

## 五、发现的问题（按严重度）

### 🔴 致命 / 功能性缺陷

**1. UDP 自动检测完全失效** — `network/udp/UdpBroadcastListener.kt:119`
`extractJsonValue()` 用的正则是 `"key":\s*"([^"]*)"`，**只匹配字符串值**。而 PC 端 `PacketUDPBroadcast::ToJson()` 序列化出的 `pcbuPort` 是**数字** `8080`、`isManual` 是**布尔** `false`，都带引号才匹配。结果 `pcbuPort == null` → `parseBroadcastData()` 返回 null → `onDeviceFound` 永不回调 → **「靠近电脑自动弹通知」这条核心体验链路等于没走通**。
修复：改用 `org.json.JSONObject` 解析（工程里已在用），或把正则放宽到 `"key"\s*:\s*("([^"]*)"|([\d.]+))`。

**2. 前台服务可能直接崩溃** — `service/UnlockListenerService.kt:159-166`
`startForeground()` 只在 `POST_NOTIFICATIONS` 已授权时才调用。Android 13+ 用户拒绝通知权限时，`startForegroundService()` 后 5 秒内未调用 `startForeground()` 会抛 `ForegroundServiceDidNotStartInTimeException` → 闪退（或 ANR）。而且 `MainActivity` 里「无论权限结果如何都启动服务」的设计让这条路径很容易被触发。
修复：无论有无通知权限都必须调用 `startForeground()`；无权限时用极简低优先级通知兜底。

**3. 蓝牙解锁通知用户根本看不见** — `service/UnlockListenerService.kt:171-189, 526`
「检测到电脑解锁请求」这条通知（ID 101）投递在 `CHANNEL_ID = "pcbu_unlock_listener"` 上，而该渠道创建时是 `IMPORTANCE_MIN`。Android 8+ 渠道重要级别决定一切，代码里设的 `PRIORITY_HIGH` 被忽略 → 通知**无声音、无震动、被折叠**，锁屏场景下基本等于不提醒。
修复：给「解锁请求」单独建一个 `IMPORTANCE_HIGH` 渠道。

### 🟠 高（会静默失效 / 用户体验受损）

**4. 网络变化监听在 Android 8+ 永不触发** — `receiver/NetworkStateReceiver.kt`、`receiver/ServiceRestartReceiver.kt:41-49`
`android.net.conn.CONNECTIVITY_CHANGE` 在 targetSdk ≥ 26 时**已禁止清单静态注册**。这两个 Receiver（以及 `ServiceRestartReceiver` 三路触发中的一路）实际上永远收不到广播，属于「写了但没用」。`NetworkStateReceiver` 整个文件可视为死代码。
修复：改用 `ConnectivityManager.registerDefaultNetworkCallback()` 动态注册。

**5. 保活机制大概率被系统拒绝** — `receiver/KeepAliveReceiver.kt:83-97`、`worker/KeepAliveWorker.kt:95-107`、`AndroidManifest.xml:47-48`
链路依赖 `SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM`。Android 13+ 起 `SCHEDULE_EXACT_ALARM` **默认不授予**，且 `USE_EXACT_ALARM` 是受限权限，仅闹钟/日历类应用可通过 Google Play 审核。这里两个都声明了，实际运行时会抛 `SecurityException` → 被 catch 吞掉 → 只剩 15 分钟粒度的 WorkManager，保活强度远低于设计预期。同时 `USE_EXACT_ALARM` 上架合规风险明确。
修复：优先用 `setAndAllowWhileIdle`（无需特权），并评估是否放弃 `USE_EXACT_ALARM`。

**6. UDP 端口配置自相矛盾** — `ui/screens/PairingScreen.kt:74,249` vs `ui/screens/SettingsScreen.kt:79-94`
设置页允许改 `udpListenPort`，但配对时**硬编码 `udpPort = 8888`** 上报给 PC，同时服务按 `prefs.udpListenPort` 监听。用户一改端口，PC 就会往旧端口广播 → 自动检测彻底断掉。
修复：配对时统一读 `UserPreferences.udpListenPort`。

**7. 蓝牙读取无超时，会永久阻塞** — `network/bluetooth/BluetoothServer.kt:178-271`
`readPacket()` 在 `accept()` 回调里被同步调用，socket 没有设置读超时。若 PC 连上后未按预期发数据，协程永久挂起 → 通知永不弹出，且 WakeLock 被占用到 60 秒超时。同时 `inputStream?.read(...) ?: 0` 在返回 0 时会**死循环空转**。
修复：`withTimeout(2000)` 包裹 + 把 `?: 0` 改为 `-1` 处理。

**8. 通知栏点击解锁在「应用已在栈顶」时失效** — `MainActivity.kt:89-104` + `ui/screens/MainScreen.kt:54-64`
`pendingUnlockDeviceId` 是普通静态变量，`setContent` 里是**一次性读取**而非 `State`。当 `MainActivity` 已在栈顶时（CLEAR_TOP 只回调 `onNewIntent`，不重建 Activity），静态值更新但不会触发重组 → 生物识别弹窗不出现。
修复：改成 `mutableStateOf` / `MutableStateFlow` 并 collect。

### 🟡 中（健壮性、安全、可维护性）

**9. 密钥明文落库 + 允许备份** — `data/entity/PairedDeviceEntity.kt`、`AndroidManifest.xml:52`
`encryptionKey`、`passwordKey` 直接以明文存 Room；工程已引入 `androidx.security:security-crypto` 但**全项目未使用**；同时 `allowBackup="true"`，`adb backup` 或 root 可完整导出，等于泄露解锁凭据。建议用 `EncryptedSharedPreferences` / SQLCipher，并关闭备份。

**10. `CryptoUtils.sha256()` 是带坑的死代码** — `utils/CryptoUtils.kt:34-55`
它用的是 **SHA3-256**（与 PC 端 `EVP_sha3_256` 一致，注释也说明了），但 `SHA3-256` 需要 API 29+，在 minSdk 28 的 Android 9 上会**静默回退到 SHA-256**，而两者结果完全不同 → 一旦将来被调用就会与 PC 端不兼容。目前全项目无调用点，建议直接删除或把 minSdk 提到 29。

**11. 单槽位状态设计，多设备会串** — `service/UnlockListenerService.kt:83-90`
`pendingBluetoothDevice` / `pendingUnlockToken` 是全局单例变量。若两台 PC 同时发起蓝牙解锁，后到的请求会覆盖前一个的 token → 前一台解锁失败。

**12. 单元测试没有测到生产代码** — `src/test/.../ManualInputValidationTest.kt`
测试内部**自己复制了一份** `isValidIpAddress/isValidPort/isValidEncryptionKey`，而生产代码 `PairingScreen.ManualPairingForm` 只做了 `isNotBlank()` / `toIntOrNull()` 校验，两者根本不同源。测的是影子实现，覆盖率是假的。

**13. 蓝牙地址匹配偏弱** — `service/UnlockListenerService.kt:395-410`
先按 MAC 查，查不到再**按设备名查**。设备名可重复，存在连错设备/误授权的可能，建议只保留 MAC 匹配。

### ⚪ 死代码清单（建议清理）

`BluetoothClient`（整类未被调用）、`CryptoUtils.sha256`、`PacketCodec.decodePacket`、`BluetoothServer.sendResponse`、`PairedDeviceDao.getDeviceCount`、`UnlockListenerService.stopKeepAlive`、`Utils.NotificationManager.showDeviceDetectedNotification`、`KEEP_ALIVE_INTERVAL` 常量、`UnlockService.unlockViaBluetooth`（只返回一句提示语）、`res/values/strings.xml` 中大量未被引用的字符串（界面文案全部硬编码在 Compose 里）。

### ⚪ 发布前需要补的

- `release` 构建**未配置签名**，`assembleRelease` 只能产出未签名包；`isMinifyEnabled = false` 且 `proguard-rules.pro` 为空。
- `app/build/` 目录留在源码树里（确认已被 `.gitignore` 覆盖）。
- 无任何 README / 架构说明文档（本次报告可作为起点）。
- PC 端 `BluetoothHelper.Win.cpp:106` 注册的 SDP GUID 尾字节是 `0xe0`，而客户端（`BTUnlockClient.cpp:55` / Linux 侧）与 Android 端用的都是 `0xdf`。两者 UUID 不一致，若后续要让手机主动连 PC 的蓝牙服务会直接失败，建议核对这是有意区分还是笔误。
- 时间戳校验窗口 ±120 秒：手机与 PC 未同步 NTP 时会以「解密失败」的形式报错，错误提示不友好，建议增加「请检查设备时间」的引导。

## 六、总体结论

- **协议层扎实**：Packet 帧、加密封装、时间戳、PBKDF2 参数与 PC 端逐字段一致，说明作者是照着服务端源码严格对齐实现的，这部分质量最高。
- **架构选型合理**：Compose + Hilt + Room + 分层清晰，符合现代 Android 实践。
- **核心短板在「系统集成」而非「业务逻辑」**：UDP 解析、通知渠道、前台服务、CONNECTIVITY_CHANGE、精确闹钟 —— 5 个致命/高优问题全部集中在 Android 系统 API 的正确用法上，会直接导致「自动检测不生效」「通知看不见」「服务被杀」这三类最终用户能感知的故障。
- **当前完成度判断**：TCP 配对 + TCP 解锁链路完整可用；UDP 自动检测与蓝牙解锁链路**代码已写完但实际跑不通**（问题 1、3、4、6、7）。
- **建议修复顺序**：①UDP 解析 ②前台服务崩溃 ③通知渠道 ④网络监听改动态注册 ⑤蓝牙读超时 → 其余按严重度推进。

## 七、项目治理建议

工程存在两处结构性隐患：一是 `UnlockListenerService` 职责过载，建议把「网络链路管理」「通知」「保活」拆成独立组件；二是「先写实现、后复制测试」的测试方式，建议改为对 `PacketCodec` 和 `CryptoUtils` 补真正的契约测试（与 PC 端对齐的固定向量），这两个类才是跨端正确性的真正关口。
